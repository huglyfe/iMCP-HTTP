# Architecture

## Implemented

One native macOS process: SwiftUI main window/menu-bar panel, an application runtime, embedded loopback HTTP, OAuth, MCP dispatch, and native Reminders, Calendar, Contacts, Maps, and Photos adapters. `IMCPCore` contains protocol, authorization, service settings, and Apple access; it has no SwiftUI dependency. `IMCPHTTP` composes those objects and displays state.

```text
SwiftUI owner decisions / observed state
              |
          AppRuntime
              |
 Hummingbird HTTP -> OAuth grant check -> SwiftMCP -> ToolDispatcher
                      |                                 |
             private grant snapshot                Apple service adapters
                      |                                 |
                native consent                     Apple frameworks
```

## Selected libraries

SwiftMCP 1.13.0 provides JSON-RPC models/decoding, protocol negotiation, MCP dispatch, metadata, schemas, and tool results/errors. Hummingbird 2.27.0 provides HTTP parsing, listener lifecycle, connection/body limits, and URL-encoded form decoding. HTTPTypes 1.8.0, Logging 1.15.1, and NIOPosix from SwiftNIO 2.103.0 are explicitly declared because the adapter imports them. SwiftNIO was already part of the Hummingbird dependency graph. `Package.resolved` pins the full dependency graph.

The released official Swift MCP SDK 0.12.1 was tested against Codex's `experimental: {"codex/auth-change": {}}` initialize payload and rejected it because its capability values are strings. SwiftMCP accepts it. No dependency fork or inbound payload rewriting is required.

SwiftMCP's Server and OpenAPI traits are disabled. Its Client trait is enabled because version 1.13.0's `@MCPServer` macro always generates a typed client, even with `generateClient: false`. This uses the supported SDK surface without a fork; the application does not instantiate that client or launch subprocesses. Its built-in transport's cached session authorization and synchronous authorization callback do not fit this app's durable native approval actor. A small stateless adapter joins the SDK to Hummingbird and authenticates every request. It advertises no tool-list notifications because this transport cannot deliver them. There is no extra proxy, daemon, legacy SSE endpoint, custom JSON-RPC decoder, or Apple-data mirror.

CryptoKit supplies SHA-256 and Security supplies secure random bytes. The S256 helper is adapted with the upstream license retained; see notices. Authorization policy and native consent are app code; no library is assumed to provide a native authorization server.

## HTTP and MCP

- Bind `127.0.0.1:18765`; issuer `http://127.0.0.1:18765`; resource `/mcp`. The real Codex acceptance test proves this same-Mac HTTP profile. It is not a remote-deployment design.
- Exact Host validation; supplied Origin must equal issuer. Native requests without Origin work. No CORS grant.
- Stateless Streamable HTTP: authenticated POST with JSON response; accepted notifications return 202; GET/SSE returns 405. No resumable sessions, server-initiated requests, subscriptions, or asynchronous job protocol.
- SwiftMCP negotiates `2025-11-25`, `2025-06-18`, or `2025-03-26`. Present `MCP-Protocol-Version` headers must name a supported version. Each request binds a fresh SDK `Session` context to the HTTP version (missing header defaults to `2025-03-26`), so output schemas and structured results follow that version. Initialization still negotiates from its body. Body `_meta` cannot override the HTTP version. The context is discarded after the request; no session IDs or shared request table are exposed.
- One scoped NIO event loop owns the local listener; it shuts down on pause, cancellation, or failure. Swift concurrency handles asynchronous requests. No process-wide per-core worker pool is created.
- Limits: 32 connections, HTTP idle timeout 10 seconds, 16 KiB aggregate headers, 8 KiB individual header/URI, 64 headers, 64 KiB MCP body, 8 KiB token body. HTTP parsing stays in Hummingbird/NIO.
- Responses prohibit caching and referrer leakage; approval HTML denies embedded resources/framing. No access/request/Apple-content logger.
- App startup reports Running only from the listener's ready callback. Bind errors remain errors. Address reuse permits immediate restart after socket shutdown, without enabling port sharing. A state-directory lease prevents multiple app writers even while paused.

The version fallback follows the [2025-11-25 Streamable HTTP specification](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports#protocol-version-header).

## Authorization and storage

All clients use RFC 7591 Dynamic Client Registration at `/register`, then the same authorization-code flow with PKCE S256. Public native clients have no client secret. Registration alone grants no access: every connection still needs the owner's native approval. Names are display labels, not proof of which executable initiated a request.

Registration accepts up to eight exact HTTP loopback callbacks (`127.0.0.1`, `localhost`, or `[::1]`), with no userinfo, query, or fragment. Authorization matches the registered host and path, allowing the native callback port to change as RFC 8252 specifies; the code exchange must use the exact callback from that authorization request. Remote callbacks are not supported. No client-specific OAuth branches, metadata URL fetching, API keys, or token-pasting setup paths.

Registration is limited to ten per minute and 128 stored clients. A later registration prunes abandoned registrations older than one day; registrations with active grants remain. Registrations and grants share one atomic snapshot. There is one current storage format with no legacy migration path. Invalid stores are preserved and rejected.

DCR is the interoperability choice for this local app: it is an MCP-supported standards-based discovery fallback already documented by local clients. CIMD would add remote metadata fetching, cache policy, and URL validation without a demonstrated client requirement. See [MCP authorization](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization), [RFC 7591](https://www.rfc-editor.org/rfc/rfc7591), and [RFC 8252](https://www.rfc-editor.org/rfc/rfc8252).

Public metadata advertises the authorization/token endpoints, S256, the `apple-services` account-wide scope, and issuer response validation. Native controls alone approve requests. `AppRuntime` gates each native approval with a fresh LocalAuthentication context using device-owner authentication (including macOS password fallback), then calls the authorization actor’s decision method. Only one prompt runs at a time. One optional attempt value owns both the request ID and a unique attempt ID; the UI derives its pending state from it. The attempt identifier prevents a cancelled or superseded prompt from completing another request; authorization snapshots cancel prompts when requests disappear, and pause/failure/quit invalidate authentication. The actor rechecks the request and expiry before issuing a code. Deny/revoke and refresh do not prompt. The authenticator is injectable for tests; no environment-based authentication bypass exists. Callbacks include `state` and `iss` on approval and denial. No arbitrary client-metadata fetching.

`/authorize` creates a request and redirects to its stable `/approval?id=...` page, so browser refresh cannot create another request. That page quietly polls `/approval/status` for a boolean; status checks neither consume nor expose the callback. On a decision it navigates once to `/approval`, which issues the standard OAuth redirect. The inline script/style use a fresh CSP nonce; polling is same-origin, sequential, time-limited, and credential-free. Network errors stop polling and offer a manual retry of the same request; expiry requires a new login from the client. Reopening an expired or consumed approval link shows a readable end-of-request page. No browser endpoint can approve access.

Pending approvals expire after three minutes; codes after one minute. A native decision gives its callback a full one-minute delivery window even when approval occurs near the pending deadline. Codes are single use, hashed in memory, and bound to client/callback/resource/PKCE. Limits: eight pending requests, eight codes, ten authorization attempts per minute, and 64 active grants. Restart/pause drops pending requests and codes.

Each grant has independent opaque access and refresh tokens. Access expires after 15 minutes. Refresh rotates both credentials, invalidating the previous access token; replay of one of the last 128 refresh hashes revokes that grant family. Older refresh tokens still fail but cannot identify the family. Revocation rejects subsequent bearer requests and refresh. It cannot undo a completed or already-started mutation.

`AuthorizationStore` serializes transitions. `grants.json` contains only credential hashes, grant IDs/timestamps, expiry, revocation state, and registered public-client metadata. Save writes a private sibling, synchronizes it, and atomically renames it before publishing in-memory state. Directory permissions are 0700, grant file 0600. No recoverable app secret or database server. Invalid/mismatched stores fail closed without replacement. `services.json` stores sets of enabled service IDs and disabled tool names. State is under Application Support/iMCP-HTTP; development overrides can isolate it.

## Apple services and app ownership

A single SwiftUI `Window` presents Services, Connections, and Setup with a native segmented picker below the title bar, one content area, and a normal Dock icon and Command-Tab presence. The familiar `MenuBarExtra` panel retains server/service switches, pending approvals, Open, and Quit. Both observe the same `AppRuntime`; closing the window does not stop it. The application delegate starts the listener at launch and handles every termination route with asynchronous listener shutdown before allowing exit. There is no separate Settings scene or sidebar redesign. Services preserves colored switches, compact descriptions, and read-only/write grouping without enabled/disabled footers. The shared-controls note precedes the Services list. Connections holds pending decisions and red revocation controls without an explanatory footer; Setup omits its redundant footer and retains the alphabetical searchable client directory and compatibility labels.

All five services start disabled. SwiftUI exposes working service toggles and current status. The implemented `AppleService` cases define menu order; future inventory stays in the plan. Individual tool switches are global across clients and accounts. Their inventory is derived from SDK metadata without constructing Apple stores or duplicating tool schemas. Changes save before the dispatcher receives the updated disabled-name set. Discovery excludes disabled tools and dispatch checks the same set before adapter access. In-flight calls may have already started. Reminders, Calendar, Contacts, and Photos request their own macOS permission only on the owner's enable action. Maps uses supplied coordinates and queries; it never requests device location. The app persists enablement after permission and settings save. Only explicitly selected services are enabled. Every approved client shares globally enabled capabilities.

The runtime owns its listener and observation tasks; their callbacks hold the runtime weakly, so releasing the owner cancels its tasks. The listener retains the state-directory lease until teardown completes. Authorization changes reach SwiftUI through one bounded `AsyncStream` snapshot observer. There is no one-second UI polling, including while paused. A one-shot timer exists only for the earliest pending visible approval and is cancelled when none remain. Service permission labels refresh when the menu/main window opens or the app becomes active; access is checked at tool dispatch regardless of UI freshness.

`AppleAccess` is the small common interface for native enablement/permission controls. Reminders and Calendar share one lazily created `EKEventStore`; Contacts has one lazy `CNContactStore`. Disabled services do not construct/query native stores. Main-actor ownership serializes native object access and writes. EventKit reminder callbacks and MapKit callbacks convert objects to Sendable value records. Photos uses lazy PhotoKit fetch results with a native fetch limit of offset + page size + one, converting only the returned page. It retains no media, library copy, or change observer. Its framework permission is read/write because PhotoKit has no read-only library authorization level; the exposed tools are read-only metadata operations.

Reminder fetches are capped at four with a 15-second timeout; Maps caps four requests with a 20-second cancellable timeout. Calendar range reads and Contacts enumeration are synchronous native operations and can briefly occupy the main actor; worker isolation is justified only if measured usage makes this a problem.

Typed SDK macros on each service's tools/models generate metadata, schemas, and dispatch. `ToolDispatcher` composes the explicit modules through the SDK's tool-provider protocol plus availability. It rejects unavailable services, disabled tools, and unknown top-level arguments; Codable inputs reject unknown nested fields and null. Adapter protocols exist for native implementations and test fakes, not dynamic plugins. No manual schema registry or generic action router.

Shared helpers cover EventKit account/list access, dates, recurrence, display alarms, validation, and deletion receipts. Reminders/Calendar/Contacts keep their own record models and mutation semantics. Fetch returns compact summaries; get returns detail. No generic success/message envelope or duplicated account metadata in item results.

Tool handlers validate stateless input before adapter access. Adapters check permissions and current native state, prepare dates/alarms/recurrence before mutation, preserve omitted fields, and return the saved object. Alarm and recurrence validation does not construct native objects; the adapter prepares those objects once per write. Recurring Calendar writes additionally require the original occurrence start and an explicit `thisEvent`/`futureEvents` span. Contacts fetches individual cards with `unifyResults = false`; no linked-card merge. List/group creation names an account. Native frameworks decide account support. No automatic retry or default destination.

Queries are bounded/paginated but not snapshots. Reminders uses native completion filtering then text/date filtering; fetch snapshots omit alarms/recurrence/start/URL/location and omit notes unless text search needs them. EventKit still returns the matching set before pagination. Native date pushdown remains deferred until date-only/floating/zone semantics receive native acceptance; Calendar uses a bounded native range; Contacts stops enumeration after enough matching rows plus one. No Apple query result survives a call. See requirements for exact contracts and native feature limits. Reconnect clients after changing service enablement; the stateless transport does not broadcast discovery changes.

## Packaging and evidence

`build-app.sh` builds an ad-hoc signed, unsandboxed development bundle, identity `io.github.huglyfe.imcp-http`, with Reminders/Calendar/Contacts/Photos usage descriptions and dependency notices. It does not install a service, enable login launch, alter firewall rules, configure clients, or grant macOS permission. Production signing/notarization, permission stability across upgrades, and distribution remain unverified.

Automated evidence includes authorization/persistence failures, HTTP protocol boundaries, dispatch/date validation, exclusive app-state ownership, direct AppRuntime startup/pause/restart/failure, owner-release, and failed-save tests, and an opt-in real Codex CLI 0.160.0 login/typed Reminders, Calendar, Contacts, Maps, Photos fixture/restart/revoke test. The Codex fixture uses dynamic registration and invokes the native decision API directly, uses a unique temporary credential, and creates no model turn. A separate OpenCode 2.0.20 fixture proves dynamic registration/login and a persisted server grant using isolated client state. Its status command does not prove fresh authorized access, so OpenCode tool/restart/revoke acceptance remains pending. Approval-boundary tests use fake authentication to verify success, cancelled/failed/unavailable authentication, retry, duplicate prompts, denial, expiry, pause/restart and late completion; real macOS authentication success, PKCE exchange, connection_check, refresh, native revoke with subsequent rejection, and native Deny were also verified in the running app with disposable clients. Both temporary grants were revoked. Production browser-script tests cover waiting without navigation, serialized checks, network retry, and expiry. Live browser refresh preserved one request, and native Deny returned to a disposable callback. Native window close/reopen preserved the listener, and Command-Q released it. Native authentication cancellation/retry, menu-specific controls, and Apple-data acceptance remain manual gates. No automated test reads or mutates real Apple records or calls live Maps. Unsaved value objects, fake adapters, and isolated OAuth state verify the contracts without permission prompts.

Setup recipes are display-only data, independent of OAuth policy. Claude Code, Cursor desktop, Gemini CLI, OpenCode, VS Code, Windsurf, and Zed have local setup guides; individual acceptance status is explicit. ChatGPT and Claude Desktop entries explain why their hosted connector paths do not directly reach this local listener. No helper, tunnel, or client configuration is installed by the app.
